# 힘찬짐 공통 백엔드

회원용 웹과 직원용 관리자가 함께 사용하는 NestJS + PostgreSQL API입니다. 실제 결제 없이 데스크 직원이 구매내역을 등록합니다. 가상 회원만 사용하며 기존 과제와 분리된 `hw2` 스키마만 읽고 씁니다.

## 실행

Node.js 22 이상, pnpm이 필요합니다.

```sh
pnpm install --frozen-lockfile
cp .env.example .env
# .env에 실제 연결값과 최초 관리자/가상회원 암호를 입력합니다.
pnpm db:setup
pnpm db:seed
pnpm build
pnpm start
```

기본 포트는 4100입니다. `GET /health`로 DB 연결 상태를 확인합니다. Render에서는 루트 디렉터리를 이 저장소로 지정하고 build `pnpm install --frozen-lockfile && pnpm build`, start `pnpm start`를 사용합니다. DB 준비와 seed는 최초 1회 별도로 실행합니다. 운영 시작마다 기존 계정을 재설정하지 않습니다.

기존 DB의 이번 변경은 백업 후 `pnpm db:migrate`로 적용합니다. `scripts/migrations/20261106_entity_lifecycle.sql`은 세 업무 테이블에 nullable `deleted_at` 열만 멱등 추가하고, `20261106_notification_preferences.sql`은 수신설정·동의변경 감사 테이블만 추가합니다. 기존 회원은 자동 동의 처리하지 않습니다. 마이그레이션은 트랜잭션과 공통 advisory lock으로 실행하며 시작 명령에는 포함하지 않습니다. 초기 schema에도 같은 내용을 반영했습니다. 운영 DB 백업·마이그레이션·배포는 별도 운영 절차입니다.

| 환경변수 | 용도 |
| --- | --- |
| DATABASE_URL | PostgreSQL 연결 문자열 |
| DATABASE_SSL | `true`이면 TLS 연결. 현재 코드의 인증서 검증 옵션은 `rejectUnauthorized:true` |
| PORT | 기본 4100, Render가 지정한 값 사용 가능 |
| INITIAL_ADMIN_EMAIL | 최초 관리자 이메일 |
| INITIAL_ADMIN_PASSWORD | 최초 관리자 비밀번호, 8~128자 |
| SAMPLE_MEMBER_PASSWORD | 가상 시연 회원 공통 비밀번호, 8~128자 |

`.env`는 Git에서 제외됩니다. 실제 암호와 토큰은 로그에 기록하지 않습니다. 현재 `DATABASE_SSL=true`일 때 TLS를 사용하되 인증서 검증은 `rejectUnauthorized:true`입니다. 인증서 검증을 유지하며, 별도 CA가 필요한 환경에서는 제공업체 CA 신뢰 설정을 추가해야 합니다.

## 시연 데이터

`db:setup`과 `db:seed`는 반복 실행할 수 있습니다. seed는 기존 계정·암호·이용권을 덮어쓰지 않으며, 새 가상회원 계정이 생성될 때만 그 회원의 자료를 생성합니다. 관리자 이메일이 이미 존재하면 변경하지 않습니다.

| 이메일 | 상태 |
| --- | --- |
| demo.member1@example.com | 현재 이용권, 지난 이용권, 미래 예약, 취소 이력 |
| demo.member2@example.com | 7일 내 만료, 잔여 횟수 있음 |
| demo.member3@example.com | 만료된 이용권 |
| demo.member4@example.com | 완료·노쇼로 10회 소진 |

트레이너 3명, 10·20·30회 이용권 종류와 완료·노쇼·취소·예약됨 데이터를 포함합니다. 이름/연락처/이메일은 가상값입니다. 각 회원의 암호는 환경변수 `SAMPLE_MEMBER_PASSWORD`입니다.

## API와 인증

이 저장소의 `API.md` 계약을 구현합니다. 독립 저장소를 배포해도 아래 경로는 동일합니다.

- 인증: `POST /auth/signup`, `/auth/login`, `/auth/logout`, `/auth/change-password`, `GET /auth/me`
- 공통: `GET /catalog`
- 회원: `GET /member/dashboard`, `PATCH /member/profile`, `POST /member/reservations`, `POST /member/reservations/:id/cancel`, `POST /member/reservations/:id/reschedule`, `GET/PATCH /member/notification-preferences`
- 직원: `/admin/dashboard`, `/admin/members`, `/admin/catalog`, `/admin/passes`, `/admin/reservations`, `/admin/trainers`, `/admin/pass-types`
- 관리자 전용: `GET/POST /admin/staff`, `PATCH /admin/staff/:id`, `POST /admin/staff/:id/reset-password`

클라이언트는 Next.js의 같은 출처 `/api/...` 프록시를 호출합니다. 프록시가 `gym_session` HttpOnly 쿠키를 읽어 백엔드에 `Authorization: Bearer TOKEN`으로 전달합니다. 회원가입·로그인은 백엔드에서 토큰과 사용자 정보를 반환하고 프록시가 토큰을 쿠키로 옮긴 뒤 사용자 정보만 브라우저로 반환합니다. 브라우저에서 직접 토큰을 저장하지 않습니다.

직원은 관리자/일반직원으로 구분합니다. 일반직원도 회원·예약·이용권·트레이너를 관리할 수 있지만 직원 계정관리는 관리자만 가능합니다. 새 직원과 비밀번호 초기화에는 무작위 임시 비밀번호를 반환하고 최초 변경을 강제합니다. 강제 변경 중에는 본인확인·암호변경·로그아웃만 허용합니다. 정지와 비밀번호 초기화는 기존 세션을 폐기합니다. 매 요청마다 활성 상태를 확인합니다. 자신의 계정 정지와 마지막 활성 관리자 제거는 거절합니다.

직원이 `POST /admin/members`로 회원을 등록할 때도 서버가 무작위 임시 비밀번호를 생성하고 최초 변경을 강제합니다. 반환된 임시 비밀번호는 직원이 안전한 경로로 전달하며 로그나 공개 문서에 남기지 않습니다. 회원 등록/수정의 `joinedAt`은 선택값이며 미래 가입일은 거절합니다. 회원 본인의 프로필 API에서는 가입일을 변경할 수 없습니다.

암호는 무작위 salt를 사용한 scrypt, 세션은 무작위 256비트 토큰의 SHA-256 해시로 저장하며 7일 후 만료됩니다. 로그인은 IP/이메일별 실패 10회에 15분 제한합니다. 이 제한은 단일 프로세스 메모리 기준이므로 여러 인스턴스로 확장할 때 공유 저장소로 옮겨야 합니다.

## 데이터와 업무 규칙

6개 핵심 테이블은 accounts(인증/역할), members(회원 연락처/가입일), trainers(근무요일), pass_types(종류/가격/기간), passes(구매 당시 횟수/실결제액/만료일), reservations(시간/상태/메모)입니다. sessions(세션), pass_receipts(구매 증빙 이미지), member_notification_preferences(본인 수신설정), notification_preference_audit(동의변경 이력)를 더해 총 10개 테이블입니다. 모든 금액은 원 단위 정수입니다. 날짜·만료·월별 집계는 한국시간 기준입니다.

- 회원/이용권 1:N, 이용권/예약 1:N, 트레이너/예약 1:N입니다.
- 회원은 본인의 이용권과 예약만 조회·변경합니다. 회원 검색은 이름 또는 연락처 뒷자리입니다.
- 이용권은 10/20/30회입니다. 종류를 수정해도 판매된 이용권의 총 횟수는 바뀌지 않습니다.
- 기본 만료일은 구매일을 1일째로 센 `구매일 + 유효기간 - 1`입니다. 직원이 만료일을 별도 지정할 수 있습니다. 만료일 당일까지 이용할 수 있습니다.
- 완료·노쇼만 사용 횟수에 포함됩니다. `잔여=구매당시총횟수-완료/노쇼`, `예약가능=잔여-예약됨`으로 계산합니다. 취소는 차감하지 않습니다. 누적 횟수 값을 덮어쓰지 않아 이중 차감을 방지합니다.
- 예약은 미래의 정각부터 1시간입니다. 이용권 기간, 소유권, 근무요일, 예약가능 횟수를 확인합니다. 같은 트레이너/회원의 동시각 예약은 DB 부분 유니크 인덱스가 거절합니다. 취소하면 같은 시간에 다시 예약할 수 있습니다.
- 변경 트랜잭션은 계정 → 회원 → 트레이너 → 구매 이용권 → 예약 순서로 필요한 행을 잠급니다. 구매 등록은 회원 다음에 종류를 잠급니다. 삭제와 신규 예약/구매가 같은 회원·트레이너·종류 잠금을 공유하고, 잠금을 얻은 뒤 삭제 여부를 다시 검사합니다. 예약/상태변경/시간변경은 구매 이용권 행 잠금 후 횟수를 계산합니다. READ COMMITTED 트랜잭션과 DB 시간 중복 인덱스로 동시 변경의 일관성을 유지합니다.
- 예약됨에서만 완료·노쇼·취소로 변경할 수 있습니다. 미래예약 완료·노쇼는 거절합니다. 완료 후에도 운동메모를 수정할 수 있습니다. 트레이너 근무요일을 바꿔도 기존 예약은 보존합니다.
- 회원은 시작 전의 예약만 취소할 수 있습니다. 시작된 수업은 직원에게 문의하도록 안내하며, 직원은 예약됨 상태를 취소·완료·노쇼로 조정할 수 있습니다. 이는 수업 시작 후 회원 취소로 노쇼 처리를 회피하지 않도록 둔 현재 작업 가정이며 실제 고객의 확정 답변을 뜻하지 않습니다.
- 회원의 시간 변경은 본인·예약됨·기존 수업 시작 전 조건으로 기존 행의 시작 시각만 원자적으로 바꿉니다. 새 시각은 미래 정각·구매기간·근무요일을 확인합니다. 본인의 기존 예약 1건은 확보 횟수 계산에서 제외하므로 예약가능 0회인 마지막 1회도 이동할 수 있습니다. 같은 회원/트레이너 시각 충돌은 409이며 실패하면 원래 시각과 확보 횟수가 유지됩니다.
- 관리 요약은 활성 회원수·예약됨 건수·오늘 취소 외 건수, 활성 회원 중 14일 내 만료와 잔여가 있는 이용권, 이번 달 트레이너별 완료 횟수를 제공합니다. 삭제 트레이너의 과거 완료 통계도 보존합니다.

DB에는 이메일/연락처 유일성, 외래키/회원-이용권 소유관계, 상태/금액/횟수/정각 제약과 시간 중복 방지가 있습니다. 만료·근무요일·잔여 횟수·역할·상태전이는 백엔드에서 검증합니다. 오류는 `{statusCode,message}`로 반환하며 DB 내부 정보는 숨깁니다.

## 검증

```sh
pnpm test
pnpm test:setup
pnpm test:integration
# UI 검수용 별도 가상 DB/API를 계속 실행할 때만:
pnpm qa:isolated
```

`test`는 DB 없이 암호·날짜·규칙과 스키마 경계를 확인합니다. `test:setup`은 테스트 전용 PostgreSQL 18.6 런타임을 Git 제외 `.local/pg-runtime`에 설치합니다. 이 의존성은 배포 package/lockfile에 없고 Render 설치·시작에 포함되지 않습니다. 실행 환경에 맞는 네이티브 바이너리가 필요하며 Linux root 사용자는 별도 비특권 사용자 환경이 필요할 수 있습니다.

`test:integration`은 운영 `.env`의 DB를 사용하지 않고, 매번 임의 포트·무작위 인증정보·별도 로컬 클러스터/DB를 생성합니다. DB 이름은 `gym_test_*`, 호스트는 loopback이어야 하며 테스트 파일의 선행 guard가 이 조건을 확인한 뒤에만 앱을 가져옵니다. 완료 시 해당 임시 클러스터를 종료·제거합니다. 원격 DB를 대상으로 원본 테스트 파일을 직접 실행하면 거절합니다.

기존 인증/영수증/경쟁 회귀와 삭제·복원·시간변경·수신설정 회귀를 검증합니다. 2026-11-06 로컬 PostgreSQL 실측에서 단위/DDL 9개와 통합 9개(상위 2개 및 하위 7개)가 모두 통과했습니다. 삭제 세션 폐기·복원·과거 이력 보존, 과거 미처리 예약 삭제 차단, 마지막 1회 이동 및 충돌 rollback, 동의 기본 false·직원 거절·감사 timestamp 일치·동일 선택 멱등성, 행 잠금으로 순서를 제어한 삭제 대 예약/구매 경쟁을 포함합니다. 이번 테스트는 운영 DB나 UI 검수용 fixture를 변경하지 않았습니다.

`qa:isolated`는 회귀 테스트와 별도 클러스터를 만들고 기본 4102(`QA_PORT`로 변경 가능)에서 API를 유지합니다. 회원/직원/과거이력/마지막 1회/충돌 fixture와 임시 접근정보를 `.local/lifecycle-qa-access.json`(0600)에 저장하며 콘솔에는 경로만 표시합니다. 외부 공유/커밋하지 않습니다. Ctrl+C 시 API와 임시 DB를 정리합니다. 공용 4100 서버를 재시작하지 않습니다.

실결제·문자발송·회원 탈퇴·외부 챗봇은 이번 필수 구현 범위에 포함하지 않습니다. 최초 관리자는 환경변수로 생성하며, 운영자의 초기 비밀번호 전달은 별도 안전한 경로에서 진행합니다.

## 추가: 구매내역 이미지 첨부

직원이 구매 이용권에 영수증 이미지를 첨부하고 직원/해당 회원이 조회합니다. OCR이나 결제 진위 확인 기능은 없습니다. 삭제·수정 API는 제공하지 않습니다.

- `POST /admin/passes/:id/receipts`: `{fileName,mimeType,dataBase64}`. 저장 후 `{receipts:[{id,fileName,mimeType,dataUrl,createdAt}]}` 반환.
- `GET /admin/passes/:id/receipts`: 직원 조회.
- `GET /member/passes/:id/receipts`: 해당 이용권 소유 회원만 조회.

JPG(`image/jpeg`), PNG(`image/png`), WebP(`image/webp`)만 허용합니다. 실제 파일 magic bytes와 MIME 일치를 확인하며 디코딩 후 2MB 이하, 파일명 120자 이하, 이용권당 5개까지 허용합니다. 파일명 경로/제어문자는 거절합니다. 이용권 행잠금으로 동시에 올려도 5개 제한을 넘지 못하게 합니다. 잘못된 base64·가짜 이미지·초과 파일을 거절하며 JSON 요청 본문은 3MB로 제한합니다.

이미지는 Render 임시 디스크 대신 `hw2.pass_receipts.image_data bytea`에 저장합니다. pass_id/uploader_id FK와 생성시각으로 구매 및 업로드 주체를 추적합니다. 재배포해도 DB에 남지만 전체 DB 백업/보존은 별도 운영 관리 대상입니다. 기본 목록 응답에는 이미지가 포함되지 않고 영수증 조회 시에만 dataUrl을 반환합니다. 이용권별 실제 파일 합계는 3,000,000바이트 이하로 제한해 base64 이미지 합계가 약 4MB를 넘지 않게 합니다. 초과 시 이미지를 줄이도록 안내합니다. 프론트의 업로드 전 축소와 배포 호스팅의 응답 제한도 함께 확인합니다.

영수증 테이블의 최초 추가는 `db:setup`에 포함되어 있습니다. 이미 영수증 기능이 있는 기존 DB의 이번 추가 변경에는 앞서 안내한 `db:migrate`를 사용합니다. 자동 통합검증은 업로드/저장/본인조회/타인거절/직원권한/위장 MIME/2MB/본문3MB/총첨부3,000,000바이트/동시 5개 제한을 격리 DB에서 검증합니다.

## 추가: 등록 항목 삭제·복원

회원·트레이너·이용권 종류는 `DELETE /admin/{members|trainers|pass-types}/:id`로 소프트 삭제하고 `POST .../:id/restore`로 복원합니다. 물리 행과 기존 구매·예약·영수증은 삭제하지 않습니다. `deletedAt`을 반환하며, 삭제한 항목은 수정하기 전에 복원해야 합니다. 기본 회원 목록과 카탈로그는 활성 항목만 제공합니다. 직원은 `GET /admin/members?includeDeleted=true`, `GET /admin/catalog?includeDeleted=true`로 전체를 확인합니다. 공통 `/catalog`에는 삭제 조회 우회 기능이 없습니다.

회원·트레이너에 `booked` 예약이 하나라도 있으면 409로 거절합니다. 과거 미처리 예약도 직원이 먼저 완료·노쇼·취소로 처리해야 합니다. 종류 삭제는 기존 구매의 횟수·기간·예약 효력을 유지하고 새 구매 등록만 막습니다. 회원 삭제는 로그인·기존 세션·본인 API와 신규 구매를 차단하며, 복원해도 폐기된 세션은 되살아나지 않습니다. 이메일/전화 UNIQUE를 유지하므로 삭제한 신원을 다른 회원이 차지할 수 없습니다. 직원은 보관된 구매·예약·영수증을 계속 조회합니다.

## 추가: PT 피드백·예약 안내 수신설정

본인만 `GET/PATCH /member/notification-preferences`로 카카오톡/문자 수신 여부를 저장합니다. 초기값은 모두 false이고 변경 시각은 null입니다. PATCH는 `{kakao:boolean,sms:boolean}` 두 실제 boolean만 받으며 다른 회원 ID 등의 추가 필드는 거절합니다. 직원은 대신 변경할 수 없습니다. 실제 선택이 바뀔 때만 설정과 감사 이력(회원·변경 계정·변경 전후 값·같은 DB 시각)을 한 트랜잭션으로 저장합니다. 동일 설정을 다시 보내면 시각이나 이력을 추가하지 않습니다.

실제 카카오톡/문자 발송, 예약 알림 스케줄, 광고성 마케팅 수신동의는 구현 범위가 아닙니다.

### 트레이너 포털

기존 DB는 백업 후 `pnpm db:migrate`로 `20261106_trainer_portal.sql`까지 적용하세요. 운영 DB에 자동 실행하지 않습니다. 신규 설치의 `db:setup`도 같은 반복 가능한 마이그레이션을 적용합니다. 기존 예약은 승인 상태로 보존하며, 관리자만 트레이너 프로필에 별도 `trainer` 계정을 연결하거나 임시 비밀번호를 재발급합니다. 연결 후 새 예약·시간 변경은 승인 대기입니다. 자세한 필드·권한·오래된 화면 충돌 처리는 [API.md](./API.md)의 Trainer portal 계약을 따릅니다.
