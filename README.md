# 힘찬짐 공통 백엔드

회원용 웹과 직원용 관리자가 함께 사용하는 NestJS + PostgreSQL API입니다. 실제 결제 없이 데스크 직원이 구매내역을 등록합니다. 가상 회원만 사용하며 기존 과제와 분리된 `hw2` 스키마만 읽고 씁니다.

## 실행

Node.js 22 이상, pnpm이 필요합니다.

```sh
pnpm install --frozen-lockfile
cp .env.example .env
# .env에 실제 연결값과 최초 관리자/가상회원 암호를 입력합니다.
pnpm db:setup
pnpm db:seed
pnpm build
pnpm start
```

기본 포트는 4100입니다. `GET /health`로 DB 연결 상태를 확인합니다. Render에서는 루트 디렉터리를 이 저장소로 지정하고 build `pnpm install --frozen-lockfile && pnpm build`, start `pnpm start`를 사용합니다. DB 준비와 seed는 최초 1회 별도로 실행합니다. 운영 시작마다 기존 계정을 재설정하지 않습니다.

| 환경변수 | 용도 |
| --- | --- |
| DATABASE_URL | PostgreSQL 연결 문자열 |
| DATABASE_SSL | `true`이면 TLS 연결. 현재 코드의 인증서 검증 옵션은 `rejectUnauthorized:true` |
| PORT | 기본 4100, Render가 지정한 값 사용 가능 |
| INITIAL_ADMIN_EMAIL | 최초 관리자 이메일 |
| INITIAL_ADMIN_PASSWORD | 최초 관리자 비밀번호, 8~128자 |
| SAMPLE_MEMBER_PASSWORD | 가상 시연 회원 공통 비밀번호, 8~128자 |

`.env`는 Git에서 제외됩니다. 실제 암호와 토큰은 로그에 기록하지 않습니다. 현재 `DATABASE_SSL=true`일 때 TLS를 사용하되 인증서 검증은 `rejectUnauthorized:true`입니다. 인증서 검증을 유지하며, 별도 CA가 필요한 환경에서는 제공업체 CA 신뢰 설정을 추가해야 합니다.

## 시연 데이터

`db:setup`과 `db:seed`는 반복 실행할 수 있습니다. seed는 기존 계정·암호·이용권을 덮어쓰지 않으며, 새 가상회원 계정이 생성될 때만 그 회원의 자료를 생성합니다. 관리자 이메일이 이미 존재하면 변경하지 않습니다.

| 이메일 | 상태 |
| --- | --- |
| demo.member1@example.com | 현재 이용권, 지난 이용권, 미래 예약, 취소 이력 |
| demo.member2@example.com | 7일 내 만료, 잔여 횟수 있음 |
| demo.member3@example.com | 만료된 이용권 |
| demo.member4@example.com | 완료·노쇼로 10회 소진 |

트레이너 3명, 10·20·30회 이용권 종류와 완료·노쇼·취소·예약됨 데이터를 포함합니다. 이름/연락처/이메일은 가상값입니다. 각 회원의 암호는 환경변수 `SAMPLE_MEMBER_PASSWORD`입니다.

## API와 인증

이 저장소의 `API.md` 계약을 구현합니다. 독립 저장소를 배포해도 아래 경로는 동일합니다.

- 인증: `POST /auth/signup`, `/auth/login`, `/auth/logout`, `/auth/change-password`, `GET /auth/me`
- 공통: `GET /catalog`
- 회원: `GET /member/dashboard`, `PATCH /member/profile`, `POST /member/reservations`, `POST /member/reservations/:id/cancel`
- 직원: `/admin/dashboard`, `/admin/members`, `/admin/passes`, `/admin/reservations`, `/admin/trainers`, `/admin/pass-types`
- 관리자 전용: `GET/POST /admin/staff`, `PATCH /admin/staff/:id`, `POST /admin/staff/:id/reset-password`

클라이언트는 Next.js의 같은 출처 `/api/...` 프록시를 호출합니다. 프록시가 `gym_session` HttpOnly 쿠키를 읽어 백엔드에 `Authorization: Bearer TOKEN`으로 전달합니다. 회원가입·로그인은 백엔드에서 토큰과 사용자 정보를 반환하고 프록시가 토큰을 쿠키로 옮긴 뒤 사용자 정보만 브라우저로 반환합니다. 브라우저에서 직접 토큰을 저장하지 않습니다.

직원은 관리자/일반직원으로 구분합니다. 일반직원도 회원·예약·이용권·트레이너를 관리할 수 있지만 직원 계정관리는 관리자만 가능합니다. 새 직원과 비밀번호 초기화에는 무작위 임시 비밀번호를 반환하고 최초 변경을 강제합니다. 강제 변경 중에는 본인확인·암호변경·로그아웃만 허용합니다. 정지와 비밀번호 초기화는 기존 세션을 폐기합니다. 매 요청마다 활성 상태를 확인합니다. 자신의 계정 정지와 마지막 활성 관리자 제거는 거절합니다.

암호는 무작위 salt를 사용한 scrypt, 세션은 무작위 256비트 토큰의 SHA-256 해시로 저장하며 7일 후 만료됩니다. 로그인은 IP/이메일별 실패 10회에 15분 제한합니다. 이 제한은 단일 프로세스 메모리 기준이므로 여러 인스턴스로 확장할 때 공유 저장소로 옮겨야 합니다.

## 데이터와 업무 규칙

6개 핵심 테이블은 accounts(인증/역할), members(회원 연락처/가입일), trainers(근무요일), pass_types(종류/가격/기간), passes(구매 당시 횟수/실결제액/만료일), reservations(시간/상태/메모)입니다. sessions(세션)와 pass_receipts(구매 증빙 이미지)를 더해 총 8개 테이블입니다. 모든 금액은 원 단위 정수입니다. 날짜·만료·월별 집계는 한국시간 기준입니다.

- 회원/이용권 1:N, 이용권/예약 1:N, 트레이너/예약 1:N입니다.
- 회원은 본인의 이용권과 예약만 조회·변경합니다. 회원 검색은 이름 또는 연락처 뒷자리입니다.
- 이용권은 10/20/30회입니다. 종류를 수정해도 판매된 이용권의 총 횟수는 바뀌지 않습니다.
- 기본 만료일은 구매일을 1일째로 센 `구매일 + 유효기간 - 1`입니다. 직원이 만료일을 별도 지정할 수 있습니다. 만료일 당일까지 이용할 수 있습니다.
- 완료·노쇼만 사용 횟수에 포함됩니다. `잔여=구매당시총횟수-완료/노쇼`, `예약가능=잔여-예약됨`으로 계산합니다. 취소는 차감하지 않습니다. 누적 횟수 값을 덮어쓰지 않아 이중 차감을 방지합니다.
- 예약은 미래의 정각부터 1시간입니다. 이용권 기간, 소유권, 근무요일, 예약가능 횟수를 확인합니다. 같은 트레이너/회원의 동시각 예약은 DB 부분 유니크 인덱스가 거절합니다. 취소하면 같은 시간에 다시 예약할 수 있습니다.
- 예약 시 이용권 행을 잠그고 현재 횟수를 다시 계산합니다. 예약 상태 변경도 같은 이용권부터 잠가 동시예약과 취소/차감의 경쟁을 직렬화합니다. 서로 다른 이용권으로 같은 시간에 예약하는 경쟁은 DB 인덱스로 차단합니다.
- 예약됨에서만 완료·노쇼·취소로 변경할 수 있습니다. 미래예약 완료·노쇼는 거절합니다. 완료 후에도 운동메모를 수정할 수 있습니다. 트레이너 근무요일을 바꿔도 기존 예약은 보존합니다.
- 회원은 시작 전의 예약만 취소할 수 있습니다. 시작된 수업은 직원에게 문의하도록 안내하며, 직원은 예약됨 상태를 취소·완료·노쇼로 조정할 수 있습니다. 이는 수업 시작 후 회원 취소로 노쇼 처리를 회피하지 않도록 둔 현재 작업 가정이며 실제 고객의 확정 답변을 뜻하지 않습니다.
- 관리 요약은 전체 회원수·예약됨 건수·오늘 취소 외 건수, 14일 내 만료와 잔여가 있는 이용권, 이번 달 트레이너별 완료 횟수를 제공합니다.

DB에는 이메일/연락처 유일성, 외래키/회원-이용권 소유관계, 상태/금액/횟수/정각 제약과 시간 중복 방지가 있습니다. 만료·근무요일·잔여 횟수·역할·상태전이는 백엔드에서 검증합니다. 오류는 `{statusCode,message}`로 반환하며 DB 내부 정보는 숨깁니다.

## 검증

```sh
pnpm test
pnpm test:integration
```

`test`는 DB 없이 암호·날짜·규칙과 스키마 경계를 확인합니다. `test:integration`은 `.env`의 DB에서 실제 HTTP 서버를 임의 포트로 열어 가상 검증자료를 생성합니다. 회원/직원권한·소유권·비밀번호 변경/초기화/정지·토큰폐기·마지막 1회 동시예약·시간중복·취소재예약·노쇼차감·이중변경 거절·판매횟수 보존·원시 DB 제약을 검증하고 생성한 ID만 `hw2`에서 정리합니다. 기존 시드와 다른 스키마는 변경하지 않습니다.

실결제·문자발송·회원 탈퇴·외부 챗봇은 이번 필수 구현 범위에 포함하지 않습니다. 최초 관리자는 환경변수로 생성하며, 운영자의 초기 비밀번호 전달은 별도 안전한 경로에서 진행합니다.

## 추가: 구매내역 이미지 첨부

직원이 구매 이용권에 영수증 이미지를 첨부하고 직원/해당 회원이 조회합니다. OCR이나 결제 진위 확인 기능은 없습니다. 삭제·수정 API는 제공하지 않습니다.

- `POST /admin/passes/:id/receipts`: `{fileName,mimeType,dataBase64}`. 저장 후 `{receipts:[{id,fileName,mimeType,dataUrl,createdAt}]}` 반환.
- `GET /admin/passes/:id/receipts`: 직원 조회.
- `GET /member/passes/:id/receipts`: 해당 이용권 소유 회원만 조회.

JPG(`image/jpeg`), PNG(`image/png`), WebP(`image/webp`)만 허용합니다. 실제 파일 magic bytes와 MIME 일치를 확인하며 디코딩 후 2MB 이하, 파일명 120자 이하, 이용권당 5개까지 허용합니다. 파일명 경로/제어문자는 거절합니다. 이용권 행잠금으로 동시에 올려도 5개 제한을 넘지 못하게 합니다. 잘못된 base64·가짜 이미지·초과 파일을 거절하며 JSON 요청 본문은 3MB로 제한합니다.

이미지는 Render 임시 디스크 대신 `hw2.pass_receipts.image_data bytea`에 저장합니다. pass_id/uploader_id FK와 생성시각으로 구매 및 업로드 주체를 추적합니다. 재배포해도 DB에 남지만 전체 DB 백업/보존은 별도 운영 관리 대상입니다. 기본 목록 응답에는 이미지가 포함되지 않고 영수증 조회 시에만 dataUrl을 반환합니다. 이용권별 실제 파일 합계는 3,000,000바이트 이하로 제한해 base64 이미지 합계가 약 4MB를 넘지 않게 합니다. 초과 시 이미지를 줄이도록 안내합니다. 프론트의 업로드 전 축소와 배포 호스팅의 응답 제한도 함께 확인합니다.

기존 DB에는 `pnpm db:setup`을 다시 실행해 새 테이블/인덱스를 추가합니다. 기존 7개 테이블의 행이나 스키마는 변경하지 않습니다. 자동 통합검증은 업로드/저장/본인조회/타인거절/직원권한/위장 MIME/2MB/본문3MB/총첨부3,000,000바이트/동시 5개 제한을 검증하고 검증자료를 정리합니다.
